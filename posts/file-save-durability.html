点了“保存”，数据真的安全了吗？——从缓存到落盘，理解一次文件写入

从缓存、flush 与 fsync 到原子替换，理解一次文件写入何时才算完成。

你写完一篇文档，按下 Ctrl+S，软件提示“已保存”。这时拔掉电源，重新开机后，文档一定还是刚才的内容吗？

答案是：**不能只凭“已保存”三个字判断。**它可能表示软件已经接收了你的修改，也可能表示操作系统已经接收了写入请求；至于数据是否已经写到断电后仍能保留的介质上，还要看软件执行了哪些步骤。

本文以电脑本地磁盘上的普通文件、常见的缓冲写入方式为例，沿着一次保存操作往下追。我们先看数据去了哪里，再讨论怎样避免保存中途出错时把旧文件也弄坏。

一、为什么刚保存完，重新打开就能看到新内容，仍不能证明它已经落盘？

保存时，数据通常经过这样一条路径：

编辑器中的新内容
    ↓
应用或编程语言的缓冲区（如果使用了缓冲）
    ↓
操作系统的文件缓存
    ↓
文件系统、设备驱动
    ↓
存储设备的缓存与非易失介质

缓存让程序不必每改一个字就等待存储设备完成一次写入。Windows 官方文档说明，文件写入通常先进入系统维护的缓冲区，再由系统安排写入磁盘；Linux 的 write() 手册也明确说，调用成功不保证数据已经提交到磁盘。Windows 文件缓存 · Linux write(2)

因此，两个看似相同的结果，含义可能不同：

你观察到的现象 它能说明什么 它不能说明什么
软件显示“已保存” 软件认为保存流程达到了它设定的完成条件 所有软件都采用同一种持久化策略
立刻重新打开，能读到新内容 当前系统能够读到这份新内容 断电后仍一定能读到；这次读取也可能命中缓存
写入调用返回成功 这次调用按其接口语义完成了 数据必然已经进入非易失介质

这就是第一个关键区别：“现在可读”与“故障后仍在”是两件事。

二、flush 到底在冲刷哪一层？

“刷新缓冲区”听起来像一个动作，实际上要先问：刷的是谁的缓冲区？

以 Python 的文件对象为例，f.flush() 把 Python 自己缓冲的内容交给操作系统；随后调用 os.fsync(f.fileno())，才是请求操作系统同步这个文件。Python 文档明确给出了这个调用顺序；在 Unix 上，os.fsync 调用原生 fsync()，在 Windows 上调用 _commit()。Python os.fsync 文档

下面的代码在 Windows 和 Linux 上都可以运行，并使用临时目录自动清理演示文件：

import os
from pathlib import Path
from tempfile import TemporaryDirectory

with TemporaryDirectory(dir=Path.cwd()) as directory:
    path = Path(directory) / "note.txt"

    with path.open("w", encoding="utf-8") as file:
        file.write("这是新版本\n")
        file.flush()                 # Python 缓冲区 → 操作系统
        os.fsync(file.fileno())     # 请求操作系统同步该文件

    print(path.read_text(encoding="utf-8"))

这段代码展示的是调用顺序，不是断电实验。最后的读取只能验证当前系统读到了新内容，不能模拟突然断电。

在 Linux 上，fsync() 会同步文件内容及相关元数据，并等待设备报告传输完成；但它不一定同步包含这个文件名的目录项。Windows 提供的 FlushFileBuffers 则用于要求系统把指定文件的缓冲数据写向设备。两者属于不同平台的接口，不能把一边的全部文件系统语义直接套到另一边。Linux fsync(2) · Windows FlushFileBuffers

三、同步了文件，为什么保存仍可能出问题？

因为“保存安全”至少包含两个不同目标：

  1. 持久性：程序报告完成后，遇到约定范围内的故障，新内容还能找回来。
  2. 原子性：保存过程中出错时，不让读者看到只写了一半的新版本，或把完整的旧版本直接改坏。

fsync 主要回答“已经写入的内容何时要求同步”；它本身不会把多次写入自动变成一个不可分割的动作。假如软件直接打开原文件、清空旧内容、再逐段写入新内容，那么写到一半崩溃时，文件就可能只剩半篇。即使事后对这个半成品调用 fsync，它也不会变回完整文档。

以 Linux 上同一文件系统内替换已有文件 为例，更稳妥的保存流程通常是：

旧文件仍可用
    ↓
在同一目录写完整的新临时文件
    ↓
fsync(临时文件)：同步新内容
    ↓
rename(临时文件, 正式文件)：一次性替换可见的文件名
    ↓
fsync(父目录)：同步目录项的变化
    ↓
再向用户报告“保存完成”

这里的 rename 解决的是其他进程看到旧版本还是新版本的问题：在上述条件下，替换已有路径时不会出现一个“正式文件名暂时不存在”的窗口。文件 fsync 和目录 fsync 解决的是另一层问题：新内容及文件名变更是否按预期持久化。调用都要检查错误，不能只执行而不看结果。Linux rename(2) · Linux fsync(2)

这是一种解释机制的 Linux 示例，不是所有编辑器的实际实现，也不是可原样照搬到 Windows、网络文件系统或云盘同步目录的通用配方。真实应用还需要按所在平台、文件系统和故障模型设计保存流程。

四、回到最初的问题

当你按下 Ctrl+S，至少要区分三句话：

写入成功：某一层接受了新数据。

同步完成：程序要求系统把相关数据推进到持久化边界，并收到了完成报告。

保存过程可靠：除了同步内容，还处理了写到一半、替换文件名和错误返回等问题。

它们不是同义词。正常使用文档软件时，我们通常不必手动执行这些系统调用；但设计编辑器、数据库或重要配置文件的保存逻辑时，必须说明自己承诺的是哪一层“成功”。即使调用了同步接口，硬件故障、设备未兑现写入承诺等问题也不在应用单靠一次系统调用就能消除的范围内。SQLite 关于原子提交与存储假设的说明

一句话记住：保存按钮是应用给出的承诺；要理解这个承诺有多强，就要追问数据经过了哪些缓冲区、何时同步，以及旧版本是怎样被替换的。
